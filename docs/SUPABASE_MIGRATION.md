# Moving from localStorage to Supabase

The app already talks to storage only through the repository interfaces in
`packages/core/src/data/repos.ts`. Today one adapter implements them: `KeyValueAdapter`
(`packages/core/src/data/adapters/keyValue.ts`), over localStorage on the web and an
AsyncStorage-backed memory mirror on phones. Adding Supabase means writing a second adapter in
`packages/core` (so web and mobile share it) and swapping it in `apps/web/src/data/index.ts` and
`apps/mobile/src/data.ts`; UI, store and domain code stay the same.

## 1. Database

`supabase/schema.sql` is an **unwired draft** that mirrors `packages/core/src/data/models.ts`:

| Model (camelCase)        | Table (snake_case)    | Notes |
|--------------------------|-----------------------|-------|
| `User`                   | `auth.users` + `profiles` | password hashing moves to Supabase Auth; `passwordHash/Salt` disappear |
| `Household`, `Member`    | `households`, `household_members` | max 2 members enforced by trigger |
| `Recipe`                 | `recipes`             | built-ins have `household_id = null`; ingredients/prep/steps as jsonb |
| `Favorite`               | `favorites`           | |
| `PlanItem`, `PlanDay`    | `plan_items`, `plan_days` | unique per (household, date, slot) / (household, date) |
| `CookLog`                | `cook_log`            | rotation memory |
| `ShoppingItem`, `ShoppingCheck`, `PantryItem` | `shopping_items`, `shopping_checks`, `pantry_items` | the list itself stays derived in `packages/core/src/domain/shopping.ts` |
| `PrepTask`               | `prep_tasks`          | regenerated by the client after plan changes (or move to an edge function) |
| `Swipe`, `Match`         | `swipes`, `matches`   | partner choices hidden by RLS; progress via `swipe_progress()` RPC; a trigger creates the match when every member liked a card (replaces `isMatch` in the store) |
| `Activity`               | `activity`            | `type` is text; Round 2 adds `recipe.imported`, `leftover.set`, `cooking.started`, `cooking.finished` |
| `ImportLog` (Round 2)    | `import_log`          | usage counter only — no link, no caption |
| `CookingSession` (Round 2) | `cooking_sessions`  | one open session per (household, key) via a partial unique index; timers as jsonb with absolute `endsAt` |

Apply it with the Supabase CLI (`supabase db push`) or paste it into the SQL editor, then seed
the 100 built-in recipes with a script that inserts `builtinRecipes` from `packages/core/src/data/seed/recipes.ts`
(`household_id = null`).

RLS: every household table is readable/writable only by members (`public.is_member(household_id)`).
Invite lookup and joining go through `lookup_invite(code)` / `join_household(code)` RPCs so
non-members never read the households table.

## 2. Adapter

Create `packages/core/src/data/adapters/supabase.ts` (framework-free; the Supabase client is passed in by each app):

```ts
export class SupabaseAdapter implements Repos {
  constructor(private sb: SupabaseClient, private bus: SyncBus) {}
  auth = {
    findUserByEmail: async () => null,           // not needed: Supabase Auth handles login
    getUser: async (id) => mapProfile(await this.sb.from("profiles").select().eq("id", id).maybeSingle()),
    // …
  };
  plan = {
    listItems: async (hid) => (await this.sb.from("plan_items").select().eq("household_id", hid)).data!.map(toPlanItem),
    upsertDay: async (hid, date, patch, by) =>
      toPlanDay((await this.sb.from("plan_days").upsert({ household_id: hid, date, ...snake(patch), created_by: by },
        { onConflict: "household_id,date" }).select().single()).data),
    // …
  };
  // households, recipes, shopping, prep, swipes, activity: same pattern
}
```

Guidelines:

- Map snake_case rows ↔ camelCase models in one place (`toPlanItem`, `snake()`), then run the
  existing zod schemas from `models.ts` on every row read (same as the localStorage tables do).
- `shopping.check()` → `upsert(..., { onConflict: "household_id,item_key" })` (last write wins).
- `swipes.addSwipe()` → upsert on `(household_id, user_id, recipe_id, date, slot)`.
- `prep.replaceAll()` → upsert on `(household_id, date, recipe_id, label)` and delete the rest
  in one RPC to keep it atomic.
- Errors: map Postgres/network errors to `StorageError` / `AppError` so the UI keeps its calm Turkish notices.
- `households.findByInviteCode` → `rpc("lookup_invite")`; `addMember` for joining → `rpc("join_household")`.

## 3. Auth

Replace `packages/core/src/services/auth.ts` internals with `supabase.auth.signUp / signInWithPassword / signOut`
and create the `profiles` row on sign-up. `SessionStore` becomes unnecessary (Supabase keeps the
session); the per-tab two-user demo then needs two browser profiles instead of two tabs.

## 4. Sync

`SyncBus` stays. Subscribe to Supabase Realtime (`postgres_changes` on the published tables,
filtered by `household_id`) and publish `{ kind: "change", tables: [table] }` on the bus; the
store already refreshes on those messages. Presence can move to a Realtime presence channel
keyed by household id with the same `{ userId, route, at }` payload.

## 5. Switch

In `apps/web/src/data/index.ts`, construct `SupabaseAdapter` when `NEXT_PUBLIC_SUPABASE_URL` is set and
fall back to `LocalStorageAdapter` otherwise. Keep the localStorage adapter for offline demo use.
Run the existing unit tests against both adapters by parameterising `packages/core/tests/unit/data/adapter.test.ts`
(point it at a local `supabase start` instance in CI).

## 6. Round 2 additions (recipe import, leftovers, cooking mode)

`create` statements were updated in place). Local data reaches the same shape through the
localStorage migrations v3–v9 in `packages/core/src/data/migrations.ts`.

Adapter notes:

- `cooking.create()` → `insert`; a second tab racing to open the same session hits the
  `cooking_sessions_open` partial unique index — catch the conflict and `select` the open row
  instead (the store already treats "an open session exists" as resume).
- `cooking.update()` for timers rewrites the whole `timers` jsonb (last write wins, like the
  localStorage table). Because timers carry absolute `endsAt`, a lost write never desynchronises
  a countdown; at worst a just-started timer must be started again.
- Realtime: `cooking_sessions` is in the publication so the partner's Bugün shows
  "Ali pişiriyor · adım 3/20" live; `households` is added for the lunch setting.
- Leftover outcomes are **derived** (`packages/core/src/domain/leftovers.ts`), never stored, so there is no
  `leftovers` table to keep in sync — only the per-evening choice is a column.
- The import route's per-household daily LLM limit lives in server memory today
  (`apps/web/src/server/import/rateLimit.ts`). With Supabase, count today's `import_log` rows with
  `provider <> 'rules'` in the route (service role) and drop the in-memory limiter. (Rows are
  written client-side after a successful draft; a server-side insert is the stricter option.)
- `GEMINI_API_KEY` / `GEMINI_MODEL` / `ANTHROPIC_API_KEY` / `YOUTUBE_API_KEY` stay server-side env vars on Vercel; nothing about
  import changes with the database move (see `docs/IMPORT.md`).

## 7. Round 3 additions (bilingual recipes, monorepo)

- **Where the code lives now:** models, repositories, migrations and the key-value adapter are in
  `packages/core/src/data`; write the Supabase adapter there too (framework-free, the client is
  passed in) so `apps/web` and `apps/mobile` share it. The web builds its data context in
  `apps/web/src/data/index.ts`, the phone in `apps/mobile/src/boot.ts`.
- **`recipes.lang`** (`'tr' | 'en'`, default `'tr'`): the language a recipe was written in. Local
  migration v10 sets `lang: "tr"` on every stored recipe; seed the column the same way.
- **`recipe_translations`** (one row per recipe and locale): `name`, `short_name`, `time_note`,
  `ingredients` (display names keyed by catalog name), `notes`, `steps`, `prep_items`, `origin`
  (`seed` | `llm` | `user`). The app's `Recipe.translations.{tr,en}` maps 1:1 onto these rows:
  the adapter reads them with the recipe (`select *, recipe_translations(*)`) and writes them with
  an upsert on `(recipe_id, locale)`. RLS follows the recipe (see the policies in `schema.sql`).
- **Built-ins:** seed their English text from `builtinRecipes[].translations.en` (origin `seed`).
- **Never translate identity:** `ingredients[].name` stays the Turkish catalog name in every
  language — shopping-list merging, "evde var" and prep tasks are keyed by it. Prep tasks store the
  source-language label; the app shows the translated one.
- **User language:** `profiles.locale` (`'tr' | 'en'`, nullable) mirrors the local `User.locale`.
